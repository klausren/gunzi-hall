## 1. 项目背景

打滚子是起源于辽宁大连的四人扑克玩法：三副牌共 162 张，对家两两配对，含抠庄、进贡、亮王、出锅等本地规则（完整规则见 `01-规则手册/打滚子规则手册-v1.1-定稿.md`，已定稿冻结）。

任老师（大连东软信息学院教师）希望做一个微信小游戏，让自己的**朋友和同好**能在手机上玩到**本地规则的原味打滚子**。

**2026-08-30 路线拍板**：走微信**「体验版」自娱路线** —— 个人主体账号、不上架、不接广告、手动添加体验成员扫码游玩。原「广告变现 + 2027-02 上架」计划**作废**。

**当前技术状态**（2026-09-15）：Cocos Creator 3.8.8 客户端 + Netty 战斗服已在微信小游戏**真机跑通**（能入座、能出牌），但**完整一局尚未端到端验证过**。

**2026-09-17 范围拍板**：多真人同房**不纳入本期**——本期只做「**1 真人 + 3 bot**」（方案 A），4 真人同桌（方案 B）排在 MVP 之后，改动清单见附录二。详见附录一 Q1。

## 2. 要解决的问题

| # | 痛点 | 具体表现 |
|---|---|---|
| P1 | **凑不齐人** | 打滚子需要 4 个人同时在线，现实中约一局成本很高 |
| P2 | **线上没有本地规则** | 通用扑克平台没有大连打滚子的完整规则（抠庄、进贡、血数、出锅） |
| P3 | **朋友分散** | 想一起玩的人不在同一地点，需要「发个码就能进」的低门槛入口 |
| P4 | **没有权威的线上实现** | 目前玩家只能线下玩，无法随时开局 |

## 3. 目标用户

- **主要用户**：任老师及其朋友（大连打滚子爱好者，**多为非技术用户**）
- **次要用户**：其他被拉进体验成员的大连同好
- **使用场景**：想打牌但凑不齐 4 人时打开；或朋友之间约一局线上玩
- **设备环境**：手机微信（iOS / Android），**横屏**游玩

---

## 4. 核心目标

> **一个懂打滚子规则的人，不需要别人在旁边教，拿着手机扫码就能打完一整局。**

衡量口径：

1. 从扫码进游戏到打完第一局，**全程不需要任老师现场指导**
2. 单局全程**不白屏、不卡死、不掉线**
3. 规则判定（跟牌、进贡、结算）**与规则手册 v1.1 一致**
4. 凑不齐 4 人时，**1 个真人 + 3 个 bot** 也能正常打完

## 5. MVP 功能范围

以下为**必须做**的，每条均可独立验证：

| # | 功能 | 验收要点 |
|---|---|---|
| F1 | **入座与开局** | 扫码进入后自动入座；可主动点「新局」重置牌局（避免接入 bot 打了一半的残局） |
| F2 | **定主（亮主）** | 支持亮主 / 反主 / 确认定主；使用级牌亮（打 3 亮 3）；玩家能看懂该点哪里 |
| F3 | **扣底** | 庄家选恰好 6 张扣下；数量不对时有明确提示 |
| F4 | **出牌** | 支持点选多张同出；跟牌规则（首家花色）判定正确、拒绝时有可读原因 |
| F5 | **进贡 / 还贡** | 上一局产生的进贡关系在下一局正确体现（仅庄家上家进贡） |
| F6 | **抠底与结算** | 一局结束展示分数 / 血数 / 升级结果，与规则手册一致 |
| F7 | **Bot 补位** | 3 个 bot 自动陪打、拟人化思考（0.8~2.5s），凑不齐人也能玩 |
| F8 | **断线重连** | 杀进程 / 切后台 / 掉网后重进，牌局原样恢复 |
| F9 | **熟人入口** | 通过体验版二维码进入，无需注册登录、无广告、无内购 |
| F10 | **超时托管** | 玩家长时间不操作，系统自动代打，不阻塞牌局 |

## 6. 用户操作流程

**首次进入**

```
朋友收到体验版二维码
  → 扫码打开小游戏
  → 若卡在「连接中」，点右上角 ··· → 开发调试 → 打开调试 → 重进
  → 自动入座（牌桌上出现自己的手牌）
```

**一局流程**

```
点「新局」→ 牌局重置、进入定主
  → 【定主】选牌 → 点亮黑桃/红桃/方块/梅花（或等 bot 亮）→ 点「确认定主」
  → 【扣底】庄家选 6 张 → 点「扣底」
  → 【出牌】轮到时选牌 → 点「出牌」（重复直到手牌出完）
  → 【结算】展示本局分数/血数/升级
  → 【下一局】若有进贡关系 → 进贡 / 还贡 → 回到出牌
```

**异常恢复流程**

```
切后台 / 掉网 / 杀进程 → 重进游戏 → 自动重连并恢复牌局（无需任何操作）
```

## 7. 输入和输出

**系统接收的输入**

| 输入 | 形式 |
|---|---|
| 入座意图 | 玩家扫码进入（自动） |
| 开局意图 | 点击「新局」 |
| 亮主 | 选中的牌 + 选择的花色 |
| 扣底 | 选中的 6 张牌 |
| 出牌 | 选中的牌（可多张） |
| 进贡 / 还贡 | 选中的牌 + 对象 |

**系统产出的输出**

| 输出 | 形式 |
|---|---|
| 牌桌状态 | 自己手牌、四家的余牌数、当前墩出牌、本墩分数 |
| 阶段提示 | 当前阶段（定主/扣底/出牌/结算）、轮到谁 |
| 操作入口 | 当前阶段可用的按钮（不可用时给出原因） |
| 结算结果 | 分数、血数、升级、下一局庄家 |
| 错误反馈 | 操作被拒时的可读原因（如「有首家花色必须跟出」） |

## 8. 异常场景

| # | 场景 | 期望行为 |
|---|---|---|
| E1 | 手机与战斗服不在同一网络 / 服务未启动 | 顶栏显示**实际连接地址**与失败可能原因；按钮变为「重试连接」 |
| E2 | 游戏中途掉网 / 切后台 | 自动重连；重连成功后牌局原样恢复并提示 |
| E3 | 玩家长时间不操作 | 系统超时托管代打，牌局继续推进（不阻塞其他玩家） |
| E4 | 显存耗尽导致渲染上下文丢失 | 提示并**自动刷新一次**恢复（防无限刷新）；刷新后自动重连恢复牌局 |
| E5 | 操作不合法（没跟花色 / 扣底张数不对） | 拒绝并给出**可读原因**，不静默失败 |
| E6 | 选牌后快照刷新（牌序变化） | 已选中的牌**不能被误清除或错位** |
| E7 | 三人不足时 | bot 自动补位，牌局照常进行 |
| E8 | 首帧快照未到达 | 界面不空白：显示连接状态与可操作按钮（不出现「什么也做不了」的空白期） |

## 9. 非功能需求

| 类别 | 要求 |
|---|---|
| **包体** | 微信小游戏主包 ≤ 4MB（真机硬上限，当前 1.74MB） |
| **平台兼容** | 微信小游戏（iOS + Android）；横屏；适配不同宽高比（如 16:9 与 19.5:9） |
| **性能** | 真机稳定 30fps 以上；连续游玩 3 局以上不因资源泄漏崩溃 |
| **网络** | 支持断线自动重连；心跳保活 |
| **安全** | 会话令牌绑定玩家身份，服务端不信任客户端上报的 playerId（已实现，见 WBS T-510） |

| **合规** | 不上架、不过审，因此**不需要**版号 / 备案 / 实名 / 防沉迷 |
| **可维护** | 单文件不超过 300 行（当前 `TableUI.ts` 1284 行，见「明确不做」说明） |

## 附录二：方案 B（4 真人同桌）改动清单

> **本期不实施**，留档备查（2026-09-17 读码勘察结果）。届时按此清单施工即可，无需重新调研。

**已经就绪、不需要动的部分**（避免重复造轮子）
- 服务端所有判断点**按座位**实现：`isHuman(seat)` / `seatOnline(seat)` / `humanWaiter()`，不是「那个唯一的真人」→ **超时托管天然适用于多真人**
- 快照**按人定制**：`emit()` 对每个连接发送 `snapshotFor(sink.playerId())`，各人只收到自己的 `yourHand`，**不泄露手牌**
- `RoomManager.join(roomId, playerId, seat, sink)` 支持任意空座入座，座位被占会明确报错
- `SessionRegistry` 的 token → (roomId, playerId) 绑定天然支持多 token
- 客户端**已有视角旋转**：`TableUI.mySeat` + `relOf(seat) = (idx(seat) − idx(mySeat) + 4) % 4`，牌位与座位牌都走该公式

**必须补的 4 个改动**

| # | 缺口 | 位置 | 后果 / 改法 |
|---|---|---|---|
| B1 | **playerId 写死 = 1** | `TableUI.playerId`、`NetTest.playerId` 的 `@property` | 第二个人 join 时 `hasPlayer(1)` 命中 → 被判为**断线重连** → **直接看到第一个人的手牌**。改法：本机生成并持久化一个随机 id（`wx.storage` / `localStorage`），随 join 上报 |
| B2 | **座位写死 `'NORTH'`** | `TableUI` 的 join 调用、`onJoinedMsg` | 第二人只会得到「座位已被占用」。改法：join 不指定 seat（由服务端分配空座），客户端采纳回包 `j.seat` 并重算视角（视角公式已就绪） |
| B3 | **开局要求房满 4 人** | `RoomActor.start()` 的 `isFull()`；`ServerMain` 建房时把 3 个 bot 座一次性占满 | 若要「2 真人 + 2 bot」，房不满则**永不开局**。改法：新增「等待 N 秒仍未满 → 空座补 bot（`sitDown(new BotPlayer(...))` + `deal()`）」的定时器 |
| B4 | **`NEWGAME` 无权限校验** | `RoomActor.handleSpec` 的 `NEWGAME` 分支 | 任何玩家都能重置牌局。4 真人场景应限定庄家 / 房主 |

**验证前提**：方案 B 需要 **2–3 台真机（或 2–3 个微信号）同时在线**才能验证，与方案 A 的「1 台真机 + 3 bot」不同，需提前协调人手。
